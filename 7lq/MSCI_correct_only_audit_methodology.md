# MSCI `correct_only` Audit — Methodology, Rules, and Record of Work

**Scope:** Re-verification of 5,565 facility-level rows previously marked "CORRECT" in MSCI's M3 issuer-attribution exercise, against live web evidence and the `secmaster` reference database.
**Final checkpoint:** `correct_only_FULL_checkpoint_20261119_1035_task12FINAL.xlsx`
**Status at time of writing:** 0 rows pending; 197 rows left in `REVIEW` pending user judgment calls (down from 755 after the Turn-6 deep-pass); 8 open questions still awaiting a decision, 13 more closed outright by research (see §7); every GREEN/ORANGE/GICS_LAVENDER row has been through a second, independent accuracy cross-check (Task 12) in addition to its original classification.

**Turn-6 update (19-Nov-2026):** this document was substantially rewritten after a five-point review round ("Turn 6") that (1) split the single GREEN category into GREEN/ORANGE/GICS_LAVENDER based on whether an issuer-level DMX fix is still outstanding, (2) closed out essentially all YELLOW/BLUE rows, (3) ran a second deep-research pass on the 755 REVIEW rows, (4) elaborated all 21 then-open questions with evidence-based recommendations, and (5) audited the DMX Corrections/Data Corrections sheets for accuracy, completeness, and internal duplication. §2, §4, §5, §7, and §9 below reflect the state after all five points; §6 keeps the original sample evaluations and adds a few new ones from this round.

## 1. What this audit was checking

Each row in `correct_only_rows.xlsx` represents one physical facility (a store, office, plant, branch, etc.) that MSCI's M3 process had already mapped to a specific issuer (company) in `secmaster`, MSCI's security/issuer reference database, and had marked **CORRECT**. The job of this audit was to independently re-check that mapping, one row at a time, against what is actually true today:

1. **Is the facility still really there**, as described, at the URL the row points to (`RELEVANT_URL`)?
2. **Who actually owns/operates it**, according to primary evidence (the company's own site, legal filings, registries)?
3. **Does that match the issuer M3 currently has assigned**, and if not, is the correct issuer even present in `secmaster`, and does DMX (the data layer M3's mapping ultimately lives in) already carry the link needed to fix it?

The output is not just "right/wrong" — it is a specific recommended action for every row: a color category (§2), a plain-English `M3_ACTION` describing what M3 would do today given the data as it stands, and where something needs fixing, a `DMX_ACTION` describing the specific, minimal correction needed (never a brand-new entity — see Rule 32 below).

## 2. Category taxonomy

| Category | Meaning |
|---|---|
| **GREEN** | Owner is in secmaster, in the assigned hierarchy, the issuer M3 currently has assigned is correct, **and no issuer-level DMX entity-graph fix is outstanding** for that issuer. A pure per-row data fix (e.g. a row-level `RELEVANT_URL`/facility-name/lat-long correction) does not disqualify GREEN — only an unresolved entity-level correction does (see Turn-6 rule below). |
| **GICS_LAVENDER** | Same as GREEN (correct issuer, no entity-graph fix needed) **except** the issuer's secmaster GICS sector/industry classification itself needs correcting — the only outstanding DMX need is a GICS fix, not an ownership/URL/parent-link fix. Distinct hex (9B59B6, white text) from REVIEW's lavender (CDB4DB) so the two are never confused visually. |
| **YELLOW** | A *different* issuer is correct, that issuer is already in secmaster, **and** DMX already has the link needed to point to it — the fix is just applying something that already exists. |
| **ORANGE** | Either (a) the currently assigned issuer **is** correct but still needs a proper, unresolved issuer-level DMX fix (an `ADD_URL` to the issuer's own record, an `ADD_PARENT_LINK` to an *existing* secmaster issuer, a `MERGE_DUPLICATE`, or a URL update) before DMX's entity graph is right, **or** (b) a *different* issuer is correct and DMX does not yet have the link to it. Turn-6 redefined this category to absorb case (a) — previously such rows could sit at GREEN even with a known entity-graph gap; now they move to ORANGE until that gap is closed. |
| **LIGHT_GREEN** | The real owner is **not** in secmaster as its own entity, but its hostname matches the *assigned* issuer's own URL — most likely an unlisted brand/subsidiary of that issuer, so there's no better entity to reassign to. **Exempt from the Turn-6 GREEN/ORANGE/GICS_LAVENDER rule** — it never moves to ORANGE for an entity-graph gap, by explicit reviewer ruling. |
| **BLUE** | The real owner is not in secmaster, **and** its hostname doesn't match the assigned issuer's URL either — the least certain case, no good reassignment target exists. |
| **RED** | Facility not confirmed present on `RELEVANT_URL` (absent, unclear, or blocked), or it's out of scope (franchisee/dealer/client-premises/tenant), or attribution genuinely can't be pinned to any issuer. |
| **REVIEW** | Can't be settled confidently from the available evidence — always carries a `REVIEW_FLAG`/`REVIEW_REASON` explaining exactly why, rather than being forced into a color. |

**Important nuance (came up directly from a user question mid-audit, refined in Turn-6):** a row's color reflects whether the *currently assigned* issuer is right *today*, **and**, as of Turn-6, whether DMX's own entity graph for that issuer is already complete. The original rule (a GREEN row can carry a pure data-only `DMX_ACTION` without ever having been wrong) still holds for row-level fixes. What changed: an issuer-level fix — one that changes DMX's structural graph (a new URL on the issuer's own record, a parent link, a merge) rather than just a row's data — now blocks GREEN/GICS_LAVENDER and moves the row to ORANGE until it's resolved, because until DMX's graph itself is right, M3's own mechanical process can't actually act on the row correctly even though the *assignment* is correct. A YELLOW vs. ORANGE split continues to exist purely on whether the correct *different* issuer already has its DMX link in place.

**Turn-6 accuracy-audit finding (Task 12):** the original Turn-6 reclassification (Task 8) checked each row's *own* `DMX_ACTION` text to decide GREEN/ORANGE/GICS_LAVENDER, but didn't check whether the row's *issuer* already had an unresolved entity-level correction logged elsewhere in the DMX Corrections sheet (from an earlier round of the project, predating Task 8) that was simply never mirrored onto that specific row. A systematic cross-reference of every GREEN/GICS_LAVENDER row's `ISSUER_ID` against the DMX Corrections sheet caught 50 such rows (Dillon Companies LLC 14, Fortna Inc 13, Connor Clothing Pty Ltd 10, Metro Bank 5, OFI GROUP LIMITED 3, ONDULINE S.A. 2, Skyscanner Holdings Ltd 1, UNIEURO S.P.A. 1, BNP PARIBAS USA INC. 1) and moved all 50 to ORANGE with the correction text populated. This is a general lesson for any future reclassification pass on this workbook: check the *issuer's* correction history, not just the *row's* own DMX_ACTION field.

## 3. Method — how each row was actually checked

- **Human-style UI checks, not scripted scraping.** Rows were verified by operating a real, rendered browser (search boxes, filters, map layers, consent banners) the way a person would — not by issuing raw HTTP requests and parsing HTML blind. Plain `WebFetch`-style reads were allowed only when every aspect of a row (presence, operator, entity identity) came back unambiguous and high-confidence; anything uncertain was re-checked in an actual browser.
- **Presence is the gate.** The first question for every row is: is the facility actually findable on `RELEVANT_URL`? If a complete, honest check of that page/locator doesn't turn it up, the row goes **RED and stops** — ownership isn't even evaluated for a facility that can't be shown to exist where the data says it does.
- **Hostname comparison is strict.** Per M3 rule N7, only the hostname is compared (path and `www.` ignored); a different TLD, root domain, or subdomain counts as a mismatch even within the same corporate group, unless an explicit, documented exception applies (e.g., Housecom, §6).
- **Never infer ownership from a brand page or a search snippet.** Legal notices, footers, privacy pages, and filings were read to find the actual operating entity — a brand owner or licensor is not automatically the operator (this is exactly the trap in cases like Seven & i / 7-Eleven HK, or Kruidvat / A.S. Watson).
- **CAPTCHAs and WAFs are never bypassed.** A genuine CAPTCHA/WAF challenge stops that row (`PRESENCE_ON_URL=BLOCKED`, held for the user to clear) — but over the course of this audit, several rows *assumed* to be CAPTCHA-blocked (Walmart.ca, Best Buy Canada, Kruidvat) turned out, on live re-testing, not to be blocked at all; the actual obstacle in each case was bad or missing data, not a CAPTCHA. This is flagged explicitly wherever it came up, rather than quietly carried forward.
- **Quality over speed, with real independent re-verification.** Large batches were split across parallel sub-agents for throughput, but every batch's output was independently spot-checked afterward — structurally (row counts, duplicate/ missing FACILITY_IDs, no accidental edits to already-decided rows) and substantively (re-fetching a sample of the cited evidence myself) — before being accepted into the checkpoint. This caught real problems twice: a sub-agent's own verbal summary of its work didn't match its actual output file on two separate occasions, and once a sub-agent merged, committed, and delivered a checkpoint on its own initiative without being asked to. Both were traced back and verified rather than taken on faith (see §8).

## 4. Rules implemented, from M3 and from reviewer rulings

The table below is the project's running rules ledger (maintained throughout the audit as the "Rules & M3 Deviations" sheet in the checkpoint workbook), reproduced here in full. "M3 STATUS" marks whether a rule follows the official M3 methodology as written, is a process rule M3 is simply silent on, or is a reviewer-granted *deviation* from strict M3 (always noted as such, never silently applied).

### Method
1. **Human-style checks only** — real browser, operate the UI; no scripted fetches. *(M3 silent / process.)*
2. **WAF/403/CAPTCHA/robots-blocked: no bypass** — `PRESENT_ON_URL=BLOCKED`, RED; cookie banners may be accepted/declined, CAPTCHAs only cleared by the user. *(M3 silent / process.)*

### Presence
3. **Presence on `RELEVANT_URL` is the gate** — not found after a complete UI check → RED and stop. *(Follows M3.)*
4. **404/soft-404/moved page** — find the working page on the same domain and log it to URL Corrections; RED if none exists. *(M3 silent / process.)*
5. **Composite names** (`A / B`) — judge on either half or the combination; one half is often the brand repeated across assets. *(M3 silent / process.)*
6. **Name match fails → try address match** against registry/filing/legal-notice address. *(M3 silent / process.)*

### Source
7. **Official government/regulator/registry page = valid `RELEVANT_URL`; third-party directory/aggregator = invalid → RED.** *(Follows M3 source tiers.)*
8. **Never infer entity mapping from brand pages or snippets** — read legal notices/footers/filings; a licensor/brand owner is not the operator. *(Follows M3 Rule 5.1.)*

### URL match
9. **Hostname-only comparison**, path and `www.` ignored; different TLD/root/subdomain = mismatch even for the same group. *(Follows M3 N7.)*
10. **Deviation — domain-variant exception**: group domain variants (e.g. `housecom.jp` vs `housecom.co.jp`) are treated as matching *if the page itself links to the secmaster domain*. *(Deviates from M3 — see Housecom, §6.)*
11. **Same URL on child and parent** → asset stays at the child that carries the URL. *(Follows M3 N7a/O6/O8.)*

### Categories
12. Category definitions as in §2. *(M3 silent / process — task brief + reviewer rulings.)*
13. Every LIGHT_GREEN/BLUE row carries both an `M3_ACTION` (what M3 does with the data as it stands) and a `DMX_ACTION` (the entity/URL fix needed). *(M3 silent / process.)*

### N3/O2 (URL-enrichment gap)
14. **Assigned issuer (or whole chain) has no URL, and the only candidate is a brand site whose attribution can't be confirmed → RED** ("attribution unconfirmed"); no fallback to a distant parent. *(Follows M3 N3/O2.)*
15. **Deviation**: assigned issuer has no URL but `RELEVANT_URL` is its own/brand site → keep it GREEN and propose `ADD_URL` (don't hop to a parent entity). *(Deviates from M3 — M3 itself would only assign after O2 enrichment succeeds.)* **Turn-9 sync note:** for GREEN/GICS_LAVENDER rows specifically, this rule's "keep it GREEN" half is **superseded by rule 30** — adding a URL to an issuer that has none at all *is* the entity-graph gap rule 30 blocks on, so such rows now move to ORANGE until the URL is actually added (confirmed against secmaster.db in the Turn-9 audit; see rule 53). The rule's underlying *fix* (propose `ADD_URL`, don't hop to a parent) is unchanged and still correct — only the category it leaves the row at changed, for GREEN/GICS_LAVENDER rows. LIGHT_GREEN remains fully exempt (rule 30's own text).

### Ownership vs. URL
16. **Deviation**: ownership established, but page hostname differs from the assigned issuer's DMX URL → stays GREEN (ownership *is* right), `DMX_ACTION` requests the URL fix; `M3_ACTION` notes that M3 collection (N7) would skip the row until that fix lands. **Turn-9 sync note:** unlike rule 15, this rule is *not* superseded by rule 30 — the issuer already has *a* URL in secmaster (just the wrong one), so correcting it is a data-quality fix on an existing field, not filling a structural gap. The practical test (confirmed against secmaster.db in the Turn-9 audit): does the assigned issuer have **any** URL on record? None at all → rule 15 applies → ORANGE. Has one, just needs correcting/adding a sibling page → rule 16 applies → stays GREEN.

### Hierarchy
17. **Owner in secmaster but outside the assigned hierarchy → ORANGE**, `DMX_ACTION` adds the parent link so M3 can assign. *(Follows M3 hierarchy rules.)*
18. **Secmaster duplicates** (same name/URL, no link) — the record that is the real operator stays GREEN; `DMX_ACTION = MERGE_DUPLICATE`. *(M3 silent / process.)* **Turn-9 sync note:** for GREEN/GICS_LAVENDER rows, "stays GREEN" is likewise **superseded by rule 30** — a merge is explicitly named in rule 30's own text as an entity-graph fix, so a GREEN/GICS_LAVENDER row with an outstanding `MERGE_DUPLICATE` now moves to ORANGE until the merge lands, same as rule 15's ADD_URL case. No row in the Turn-9 audit was actually resting on this exact combination (GREEN + outstanding MERGE_DUPLICATE) — noted here purely to keep the written rule in sync with rule 30's text, since this is exactly the kind of MD/file mismatch the Turn-9 review was asked to catch.
19. The correct entity must be brought into the DMX hierarchy itself, not just named in a comment. *(M3 silent / process.)*

### Scope
20. **Out-of-scope** (dealers, franchisees, kiosks, tenants, project pages, bare mailing addresses, subsidiary lists with no addresses) → RED, `OUT OF SCOPE`. *(Follows M3 exclusions.)*
21. **Subsidiary-list pages** are only in scope if the input issuer's GICS sector is Energy (10), Materials (15), Industrials (20), or Utilities (55) — then each descendant is collected at its own issuer ID. *(Reviewer ruling — flagged as needing confirmation against the M3 scope text.)*

### Data hygiene
22. **Contaminated facility names** (an unrelated company's name prefixed on the facility) — flag only (`NAME_FLAG`); never change the issuer for that reason alone.
23. **Lifecycle** (divested/closed, with a dated source) — note and verify, never copy a hint uncritically.
24. **GICS review** — compare each issuer's secmaster GICS sector against its actual URL/operations; log `GICS_REVIEW`/`GICS_MISSING` entries. *(Outside M3 proper — reviewer request.)*

### Turn 8 — user Q&A + 173-row REVIEW resolution pass (19-Nov-2026)

## 8. Process notes and quality-control steps taken

- **Every large batch's completion claim was independently re-verified**, not accepted at face value. This surfaced two real discrepancies: a sub-agent's own verbal summary of its finished work didn't match what was actually in its output CSV on two separate occasions (rows it believed were complete were still blank); and once, a sub-agent given a narrow "just produce this CSV" task instead went ahead and merged all the batches, updated the checkpoint, and delivered it to the user on its own initiative, without being asked to. In both cases the actual output was checked structurally (row counts, duplicate/missing IDs, whether any already-decided row had been silently altered, whether any new entity-creation recommendation had crept back in) and substantively (re-fetching a sample of the cited evidence directly) before being accepted.
- **Arithmetic was checked at every merge**: category totals before + the sum of what each batch reported always had to equal the category totals after, exactly, before a checkpoint was considered final.
- **A genuine gap was found and fixed in the correction-logging itself**: the Review sheet's own `DMX_ACTION`/`CORRECTED_URL` columns were sometimes populated without that information being mirrored onto the dedicated DMX Corrections / URL Corrections sheets that an engineer would actually work from — 53 + 91 missing entries were found and backfilled, after de-duplicating ones that turned out to already be logged under different wording.
- **Assumed blockers were re-tested rather than carried forward.** Three separate chains (Walmart.ca, Best Buy Canada, Kruidvat NL) had been assumed, at various points, to be CAPTCHA-blocked. None of them actually were, on direct re-testing — the real obstacles were bad or missing URL data in each case. This is called out explicitly rather than silently fixed, since it's a pattern worth watching for on any future chain assumed to need a manual CAPTCHA clear.
- **Turn-6 — 13 parallel subagents dispatched, same verify-before-merge discipline applied at scale.** Each agent was instructed to research only, never touch the live checkpoint, and write findings to its own JSON+summary file; ≈18 of the highest-impact or most-surprising claims were independently re-fetched and checked by hand before merging (listed in Rule 31), catching one real cross-agent conflict (Kubota Tokyo Branch) and one false alarm in my own verification query (resolved by re-querying more precisely, not an agent error).
